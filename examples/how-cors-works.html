The API writes a guest list, and the browser checks your name on it.

Your page on https://app.example.com calls fetch() on https://api.example.com/orders. The reply arrives, but the browser hands it to your code only if the reply names your origin.

Marked: the guest list check, where the browser decides if your code may read the reply. The drawings below zoom into each part.

In plain words. Think of the browser as a doorman between your page and every other site. It pins your page's name on each request and knocks first when a request looks risky. When the reply comes back, it reads the API's guest list. Your name is on it: your code gets the reply. It is not: your code gets an error.

  1. The browser pins your origin on the request as a name badge.

    In plain words. Your page's origin is where it came from: scheme, host and port. app.example.com and api.example.com differ in host, so they are two origins. That makes this call cross-origin.

    Under the hood. Two URLs share an origin only when scheme, host and port all match. On this call the browser adds Origin: https://app.example.com. Origin is a forbidden request header, so fetch() cannot set or fake it.

    name badge = Origin header

  2. Before a risky request, the browser knocks first.

    In plain words. A PUT, or a request with a login header, could change data. So the doorman knocks on the API's door first and asks: may I bring this in?

    Under the hood. This knock is the preflight, an OPTIONS request sent without cookies. The browser sends one for a method other than GET, HEAD or POST, for a header off the safelist such as Authorization, and for a Content-Type outside three form types, so application/json counts. The answer needs a 2xx status and matching Access-Control-Allow-* headers.

    OPTIONS /orders
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization

204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: PUT
Access-Control-Allow-Headers: authorization
    doorman = the browserknock = preflight (OPTIONS)door = the API's CORS handler

  3. Your code gets the reply only if the guest list names your origin.

    In plain words. The API sends its guest list back with the reply. The doorman holds the reply and reads the list. on the list your code gets the reply. not on it your code gets an error.

    Under the hood. The check passes when Access-Control-Allow-Origin matches the request's Origin exactly, or is *. The header holds one origin, not a list, so an API that allows several echoes the one it got and adds Vary: Origin. On failure, fetch() rejects with a TypeError, and only the console says why.

    guest list = Access-Control-Allow-Originreply box = Response

    The server never blocks anything. The browser does.

  4. With cookies, the list must name you exactly.

    In plain words. By default, a cross-origin fetch() sends no cookies. Ask for them, and the rules get stricter: anyone (*) no longer counts, and the list must also say yes to cookies.

    Under the hood. With credentials: 'include', the check fails on Access-Control-Allow-Origin: * and requires Access-Control-Allow-Credentials: true. The preflight itself never carries cookies, but its answer needs the same two headers.

    fetch('https://api.example.com/orders', {
  credentials: 'include', // send cookies
});
    anyone = *stamp = Access-Control-Allow-Credentials: true

CORS hides the reply. It does not stop the request.

A plain GET or form POST skips the knock, so the server runs it even when the browser then hides the answer, and curl ignores CORS completely. Protect writes with auth and CSRF defenses such as SameSite cookies, not with CORS.

Push further

Does mode: 'no-cors' make the error go away?

The error goes away, and so does the data. You get an opaque response: status 0, no headers, and a body your code cannot read.

Why does a server crash look like a CORS error?

Error pages often come from a layer that skips the CORS headers. A 500 without a guest list fails the check, so the console blames CORS, not the crash.

Can the browser skip the knock next time?

Yes, for a while. Access-Control-Max-Age caches the answer: 5 seconds by default, capped at 2 hours in Chromium and 24 hours in Firefox.

Simplified on purpose. One page, one API, no redirects; Access-Control-Expose-Headers and the null origin are left out.
