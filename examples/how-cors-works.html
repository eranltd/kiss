The browser hides the reply unless the server lists your origin.

Your page on app.example.com calls fetch('https://api.example.com/orders'). The server answers, and then the browser reads one reply header to decide if your code may see the data.

  2. Doormanbrowser
  3. Call aheadOPTIONS
  4. The APIapi.example.com
  5. Guest listACAO header

Circled: the guest list, because one reply header decides whether your script sees the data. The drawings below zoom into each part.

In plain words. Your script asks another origin for data. The browser acts as a doorman: it lets the request out, then reads the reply first. The server writes a guest list on the reply (Access-Control-Allow-Origin). If your origin is on it, your script gets the data. If not, the browser drops it.

  1. An origin is scheme, host and port, all three.

    In plain words. Your page's home address (origin) has three parts: the protocol (scheme), the machine name (host) and the port. Change any one and the browser treats the other side as a stranger. The path never counts.

    Under the hood. Row 1 matches, because the path is not part of the origin. Rows 2–4 each change one part, so a fetch() to them is cross-origin. https:// implies port 443, so the 8080 in row 4 does not match.

  2. The browser sends the request, then checks the reply.

    In plain words. The doorman (browser) lets your request leave. When the reply comes back, it reads the guest list first. Your script sees the reply only if your origin is on that list.

    Under the hood. In step 2 the browser adds Origin: https://app.example.com itself; your code cannot change it. In step 3 the server sets Access-Control-Allow-Origin to that exact origin or to *. In step 4 a mismatch makes fetch() reject with a TypeError, and only the console says why.

  3. A risky request calls ahead with OPTIONS first.

    In plain words. Some requests could change data on a server that never expected them. So the browser calls ahead (preflight) and asks: may this origin send a PUT with JSON? Only a yes lets the real request out.

    Under the hood. A PUT, a JSON body or an Authorization header triggers step 2; plain GETs and form posts skip it. In step 3 the server answers with Access-Control-Allow-Methods, Access-Control-Allow-Headers and the guest list. The browser caches that yes for Access-Control-Max-Age seconds (5 by default), so each miss costs one extra round trip.

  4. With cookies, the guest list must name you exactly.

    In plain words. By default the browser leaves your cookies out of cross-origin calls. Ask for them (credentials: 'include') and the rules get stricter. The server must name your exact origin and say yes to cookies.

    Under the hood. The reply needs your exact origin in Access-Control-Allow-Origin plus Access-Control-Allow-Credentials: true. With *, the browser blocks the reply. A server for many origins checks the request's Origin against an allowlist and echoes the match back.

CORS hides the reply. It does not stop the request.

A simple POST reaches the server and runs before the browser checks any header. Guard routes that change data with auth and CSRF tokens, not with CORS.

Push further

Why does it work in curl but fail in the browser?

CORS is a browser rule that protects the user's logged-in data. curl has no page origin and no user to protect, so it never reads these headers.

Can I fix a CORS error from the frontend?

No. mode: 'no-cors' only returns an opaque reply your code cannot read, so fix the server's headers or call a same-origin proxy.

What breaks when a CDN caches the reply?

If the server echoes the request's Origin, a CDN can hand origin A's guest list to origin B. Send Vary: Origin so the cache keeps one copy per origin.

Simplified on purpose. Left out Access-Control-Expose-Headers, redirects, opaque responses and Private Network Access.
