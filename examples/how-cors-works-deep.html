The server writes a guest list, and your browser enforces it.

Your page at https://app.example runs fetch("https://api.example/orders", { method: "PUT" }). Before the PUT leaves, the browser sends an OPTIONS question, and one header in the answer decides whether your code sees anything.

Marked: the guest list in the server's answer, because the browser reads it to decide if your code gets the reply. The drawings below zoom into each part.

In plain words. Think of a club door. Your page is a guest with a name tag, and the browser is the bouncer. For anything unusual, the bouncer calls ahead first. The server writes a guest list on each answer, and the bouncer hands the answer to your code only if the list names you.

  1. Your page's name is its origin, and the browser writes the tag.

    In plain words. An origin is where your page came from. When your page, the guest, asks another origin for something, the browser pins a name tag (Origin) on the request. Your code cannot write or change that tag.

    Under the hood.

    1. An origin is scheme, host and port: https://app.example is https, app.example, port 443.
    2. http://app.example, https://api.example and https://app.example:8443 are three other origins. Another port is enough.
    3. A same-origin request skips CORS. A cross-origin fetch() runs in mode "cors" and carries the Origin header.
    4. Origin is a forbidden request header, so page script cannot forge it. curl can, so CORS protects users, not servers.
    guest = your page (app.example)bouncer = the browsername tag = Origin header

  2. A plain request goes out at once; anything else calls ahead first.

    In plain words. Some requests look like what an old HTML form could already send. The browser lets those go straight out. Anything fancier, such as a JSON body or an auth header, gets a call ahead first.

    Under the hood.

    1. Safelisted methods: GET, HEAD, POST.
    2. Headers your code sets must be safelisted: Accept, Accept-Language, Content-Language, Content-Type, and Range with one range.
    3. Content-Type must be application/x-www-form-urlencoded, multipart/form-data or text/plain.
    4. Each safelisted value is at most 128 bytes, and all of them together at most 1,024 bytes. Past that, they count as unsafe.
    5. Anything else needs a preflight: PUT, DELETE, PATCH, Authorization, any custom header, or a ReadableStream body.
    // No preflight: safelisted method and Content-Type
fetch("https://api.example/orders", {
  method: "POST",
  headers: { "Content-Type": "text/plain" },
  body: JSON.stringify(order),
});

// Preflight: application/json is not safelisted
fetch("https://api.example/orders", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(order),
});
    plain request = CORS-safelisted method + headerscall ahead = CORS preflight

    A plain request is checked after it runs. Anything else is checked before.

  3. The preflight is an OPTIONS question, and the real request waits for its yes.

    In plain words. The browser asks the server: may app.example send a PUT with a Content-Type header? Only a clear yes lets the real request out. Then the real answer is checked again.

    Under the hood.

    1. Your code calls fetch() with PUT and a JSON body.
    2. The browser sends OPTIONS /orders with Origin, Access-Control-Request-Method: PUT and Access-Control-Request-Headers: content-type. It sends no cookies and no body.
    3. The server must answer with an ok status (200–299, often 204) and matching Access-Control-Allow-Origin, -Allow-Methods and -Allow-Headers. A 404, a 401 from auth middleware, a redirect or a missing header ends the fetch here.
    4. Only now does the real PUT leave, with Origin again.
    5. The real answer needs its own Access-Control-Allow-Origin. The preflight's yes does not cover it.
    6. The promise resolves. The price is one extra round trip, say 80 ms to a far region.

Host: api.example

  4. The browser hands over the answer only if the guest list names your origin exactly.

    In plain words. The server writes one name on its guest list: your exact origin, or * for an open door. The bouncer compares it with your name tag, letter for letter. No match, and your code gets nothing.

    Under the hood.

    1. The browser reads Access-Control-Allow-Origin on the preflight answer and on the real answer.
    2. A missing header fails the fetch.
    3. * passes, but only for a request without cookies.
    4. Any other value must equal Origin exactly. https://app.example/, app.example and https://*.example all fail. The header holds one value, never a list.
    5. On a fail, fetch() rejects with a TypeError. Your code sees no status and no headers; only the DevTools console says why.
    6. On a pass, your code reads the body and seven safelisted response headers, such as Content-Type. Others need Access-Control-Expose-Headers.
    const allowed = new Set(["https://app.example", "https://admin.example"]);

app.use((req, res, next) => {
  const origin = req.headers.origin;
  if (allowed.has(origin)) {
    res.set("Access-Control-Allow-Origin", origin);
    res.set("Access-Control-Allow-Credentials", "true");
  }
  res.append("Vary", "Origin");
  if (req.method === "OPTIONS") {
    res.set("Access-Control-Allow-Methods", "GET, PUT, DELETE");
    res.set("Access-Control-Allow-Headers", "Content-Type");
    res.set("Access-Control-Max-Age", "7200");
    return res.sendStatus(204);
  }
  next();
});
    guest list = Access-Control-Allow-Originopen door = *

    One exact origin, or * without cookies. Nothing else passes.

  5. Cookies go along only when both sides opt in.

    In plain words. By default, a cross-origin fetch leaves your member card (cookies) at home. Your code must ask to send it, and the server must stamp members welcome. Then the open door no longer counts.

    Under the hood.

    1. Your code opts in with credentials: "include" (withCredentials = true in XMLHttpRequest).
    2. The preflight still carries no cookies, so auth that runs on OPTIONS answers 401 and blocks everything.
    3. The answer must carry Access-Control-Allow-Credentials: true, spelled exactly so.
    4. Access-Control-Allow-Origin must name the origin. In -Allow-Headers, -Allow-Methods and -Expose-Headers, * stops being a wildcard.
    5. If the check fails, the browser also ignores Set-Cookie on that answer.
    6. Cookie rules still apply on top: SameSite and third-party cookie blocking can keep the card home even when CORS says yes.
    const res = await fetch("https://api.example/me", {
  credentials: "include",
});
    member card = credentials (cookies)members-welcome stamp = Access-Control-Allow-Credentials: true

  6. A yes is cached for Max-Age seconds, then the browser asks again.

    In plain words. Calling ahead every time would double the trips. So after a yes, the bouncer gives your page a wristband. While it lasts, matching requests walk straight in.

    Under the hood.

    1. With no entry, a request that is not plain goes to OPTIONS first.
    2. A yes is stored for Access-Control-Max-Age seconds: 5 s when the header is missing, capped at 7,200 s (2 h) in Chromium and 86,400 s (24 h) in Firefox.
    3. While the entry lasts, a request with a cached method and headers skips OPTIONS.
    4. When it expires, or a request adds a header the entry lacks, the browser asks again.
    5. A failed answer blocks the fetch with a TypeError.

    Entries are kept per origin, URL and credentials mode, so /orders/1 and /orders/2 each get their own preflight.

CORS guards the reader, not the server.

A plain POST from any site still reaches your server and runs; the browser only hides the reply. Auth checks and CSRF protection stay your job, and curl ignores CORS completely.

Push further

Why does curl or Postman work when the browser fails?

Only browsers enforce CORS. Other clients never read the Access-Control-* headers, so a working curl proves the server runs, not that CORS is set.

Can I just use mode: "no-cors"?

You get an opaque response: status 0, no headers, and a body your code cannot read. It only fits fire-and-forget calls.

Why does every /orders/:id call send its own OPTIONS?

The preflight cache keys on the full URL, so each id is a new entry. Keep custom headers off hot paths, or serve the API from the same origin through a proxy.

Is it safe to echo the Origin back?

Only against an allowlist. Echoing any origin with Allow-Credentials: true lets every site read your users' data with their cookies. Add Vary: Origin so a CDN does not serve one site's answer to another.

How do I test my CORS setup?

Send the preflight yourself with curl -i -X OPTIONS, an Origin header and Access-Control-Request-Method, then read the Access-Control-* headers. In the browser, the DevTools console is the only place that names the reason.
