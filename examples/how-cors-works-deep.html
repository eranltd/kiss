The browser hides the reply unless the server names your origin.

Your page on app.shop.com calls fetch('https://api.shop.com/cart'). The server logs a 200, and your code still gets a TypeError.

Circled: the guest list, because the browser hands over the reply only if your origin is on it. The drawings below zoom into each part.

In plain words. Your script asks the browser to fetch from another origin. For risky requests, the browser first asks the API if that is allowed. Every answer from the API carries a guest list. The browser gives the reply to your script only if your origin is on that list.

  1. An origin is scheme, host and port, and all three must match.

    In plain words. The browser stamps every page with a return address (Origin). Two addresses match only when all three parts match. Anything else is cross-origin, and the guest list rules apply.

    Under the hood. The browser builds the origin from the page URL in three parts.

    1. Scheme. http://app.shop.com and https://app.shop.com are two origins. An HTTPS page that calls an HTTP API is also mixed content. The browser blocks that before CORS runs.
    2. Host. An exact compare after lowercasing. shop.com and www.shop.com are two origins.
    3. Port. The default port drops out, so https://app.shop.com:443 equals https://app.shop.com. A dev page on localhost:3000 that calls localhost:8080 is cross-origin.

    The browser writes the result into the Origin request header. Page script cannot set it, because Origin is a forbidden header name.

  2. A simple request goes out at once, and only the reply is held back.

    In plain words. For a plain GET, the browser does not ask first. It sends the request, receives the whole reply, then reads the guest list. No list means no reply for your script.

    Under the hood. Four steps, no preflight.

    1. fetch() defaults to mode: 'cors'. The target origin differs, so the browser runs the CORS protocol.
    2. The request is simple: method GET, HEAD or POST, with only safelisted headers. Content-Type must be text/plain, multipart/form-data or application/x-www-form-urlencoded. Each safelisted value must stay at 128 bytes or less. The browser adds Origin and sends it at once.
    3. The server runs the handler and sends the full body. Every byte crosses the network.
    4. With no Access-Control-Allow-Origin, the browser swaps the reply for a network error. fetch() rejects, so there is no status, header or body to read.

    The error text differs per browser. Chrome says Failed to fetch, Firefox says NetworkError when attempting to fetch resource., Safari says Load failed. Only the DevTools console names CORS as the cause.

  3. A riskier request waits for a yes from a preflight.

    In plain words. Some requests could change data on a server that never heard of CORS. For those, the browser asks first with a short question (OPTIONS). The real request leaves only after a clear yes.

    Under the hood. Six steps, two round trips.

    1. PUT is not a simple method. Content-Type: application/json is not a safelisted value. Either one forces a preflight, and so does any custom header, such as Authorization.
    2. The browser sends OPTIONS /cart with Origin, Access-Control-Request-Method and Access-Control-Request-Headers. A preflight never carries cookies or a body.
    3. The server answers with a 2xx status and the allow headers. A redirect, a 401 or a 404 fails the preflight. Auth middleware that rejects OPTIONS is the usual cause.
    4. The real PUT goes out, with Origin again.
    5. The server replies 200. This reply needs Access-Control-Allow-Origin too, because the browser checks both.
    6. The browser hands the body to your script.

    The browser caches each yes for Access-Control-Max-Age seconds. Without the header it keeps it 5 s. Chromium caps it at 7,200 s, Firefox at 86,400 s. The cache key includes the full URL, so /cart/1 and /cart/2 each pay their own preflight. An uncached preflight adds one round trip, roughly 50–150 ms on a phone network (estimate).

  4. The check is a plain string compare, not a pattern match.

    In plain words. The guest list holds one name or a star. The browser compares that name with your origin, character for character. Once cookies ride along, the star stops counting, and a second header must say yes.

    Under the hood. The CORS check from the Fetch spec, in order.

    1. No Access-Control-Allow-Origin header: fail. Two copies join into a, b, which never matches: fail.
    2. The value is * and the request sends no cookies: pass.
    3. The value must equal the serialized origin, such as https://app.shop.com. A trailing slash or a second origin fails.
    4. No cookies: pass. With cookies, Access-Control-Allow-Credentials must be exactly true.

    A pass still hides most response headers. Your script reads only Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified and Pragma. Name any other header in Access-Control-Expose-Headers.

  5. Cookies need your exact origin echoed back, plus a second yes.

    In plain words. A cross-origin fetch() sends no cookies by default. Ask for them, and the guest list must name you exactly. It must also say that cookies are welcome.

    Under the hood. Three steps with stricter rules.

    1. Your script opts in with credentials: 'include', or withCredentials = true on XHR. The browser attaches cookies for api.shop.com, filtered by SameSite. app.shop.com and api.shop.com are the same site, so Lax cookies go. A different site needs SameSite=None; Secure, and Safari and Firefox block or partition those by default.
    2. The server echoes the exact Origin and adds Access-Control-Allow-Credentials: true. It also sends Vary: Origin, so a CDN never serves one origin's reply to another.
    3. The check passes and the body goes to your script. On a fail, the cookie still went out and the handler still ran.
    const ALLOWED = new Set(['https://app.shop.com', 'https://admin.shop.com']);

function applyCors(req, res) {
  res.setHeader('Vary', 'Origin');
  const origin = req.headers.origin;
  if (!ALLOWED.has(origin)) return; // no headers: the browser blocks the read
  res.setHeader('Access-Control-Allow-Origin', origin);
  res.setHeader('Access-Control-Allow-Credentials', 'true');
}

// in the page on app.shop.com
await fetch('https://api.shop.com/me', { credentials: 'include' });

CORS stops your page from reading, not the request from running.

A blocked simple POST still reaches your handler and still writes, and curl ignores CORS entirely. Guard writes with auth plus CSRF tokens or SameSite cookies, because CORS only guards the reply.

Push further

Why do I see a CORS error when the server returns 500?

Error paths often skip the CORS middleware, so the 500 has no Access-Control-Allow-Origin. Read the server log first, and add the headers to error replies too.

How do I allow several origins?

The header holds one origin or *. Keep an allowlist on the server and echo the matching Origin. Always send Vary: Origin, so caches keep the replies apart.

Does mode: 'no-cors' fix it?

It sends the request but returns an opaque reply: status 0, no headers, no body. It suits fire-and-forget pings, not reading data.

Should I allowlist Origin: null?

No. Sandboxed iframes, file:// pages and cross-origin redirects send null, and any attacker can build a sandboxed iframe.

How do I test CORS without a browser?

Replay the preflight with curl -i -X OPTIONS -H 'Origin: https://app.shop.com' -H 'Access-Control-Request-Method: PUT' https://api.shop.com/cart. curl enforces nothing, so you judge the allow headers yourself.

Simplified on purpose. Left out: Private Network Access preflights, CORS for fonts, images and <script crossorigin>, and opaque replies in service workers.
