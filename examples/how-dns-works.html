One resolver asks three servers in turn, then keeps the answer.

You type github.com and press Enter. Your resolver asks a root server, a .com server and GitHub's own name server, then hands back 20.217.135.5 and keeps a copy for 60 seconds.

Marked: the librarian, because it does the whole walk and keeps copies, so a repeat question never leaves its desk. The drawings below zoom into each part.

In plain words. No one server knows every name. The librarian reads github.com right to left and asks one index per part. GitHub's own cabinet holds the address. The librarian keeps a copy for next time.

  1. Your laptop asks one question and waits.

    In plain words. Your laptop does not walk the tree. It checks its own cache first. Then it asks one librarian and waits for a finished answer.

    Under the hood. The OS stub resolver checks /etc/hosts and its cache, then sends one UDP packet to port 53 with the RD (Recursion Desired) bit set. The resolver's address comes from your network or a setting such as 1.1.1.1; this laptop uses 100.100.100.100.

    librarian = recursive resolver

  2. The librarian walks the name from right to left.

    In plain words. Each index knows only the next index down. The librarian follows the pointers until one server hands back a real address.

    Under the hood. Steps 2 and 4 are referrals: NS records for the next zone, plus glue addresses so the resolver can reach those servers. Step 6 is the authoritative A record. From this laptop, dig +trace measured the three hops at 81, 85 and 162 ms.

    $ dig +trace @1.1.1.1 github.com   (trimmed)
com.        172800 IN NS l.gtld-servers.net.
;; from c.root-servers.net in 81 ms
github.com. 172800 IN NS ns-1707.awsdns-21.co.uk.
;; from f.gtld-servers.net in 85 ms
github.com. 60     IN A  20.217.135.5
;; from ns-1707.awsdns-21.co.uk in 162 ms
    librarian = recursive resolvermain index = root server.com index = TLD server (com.)card cabinet = authoritative NSpointer = referral (NS + glue)

    Every server but the last one only says: ask someone else.

  3. The real answer is a card with an expiry time.

    In plain words. GitHub's cabinet has one drawer per kind of record. The A drawer holds the address. Every card carries an expiry time, and this one says 60 seconds.

    Under the hood. The authoritative server answers from its zone with the AA (Authoritative Answer) bit set. Each resource record carries a TTL in seconds, and a cache may shorten it but never stretch it. AAAA holds an IPv6 address; MX names a mail server.

    card cabinet = authoritative NSdrawer = record typecard = resource recordexpiry = TTL

  4. The librarian keeps copies, so the walk is rare.

    In plain words. The librarian copies every card and every pointer it gets. The next asker gets the copy at once. When a card expires, it goes in the bin, and the next question walks again.

    Under the hood. A resolver caches each record for its TTL and counts it down; two dig calls in a row show 55, then 54. The com. referral lives for 172800 s (2 days), so a later walk for any .com name skips the root.

    $ dig @1.1.1.1 github.com +noall +answer
github.com.   55   IN   A   20.217.135.5
$ dig @1.1.1.1 github.com +noall +answer
github.com.   54   IN   A   20.217.135.5
    librarian = recursive resolverclipboard = cachecard = resource recordpointer = referral (NS)bin = evicted at TTL 0

    A cached answer costs one round trip. A cold one costs four.

A changed record does not spread. Old copies expire.

Nothing pushes your edit to the resolvers. Each one serves its old copy until the TTL runs out, so lower the TTL well before a move and wait out the old one.

Push further

What if GitHub's name server is down?

github.com lists eight name servers, so the resolver tries another one. If none answer, your laptop gets SERVFAIL.

Why does a brand-new subdomain fail for a while?

If anyone asked for it before it existed, resolvers cached the NXDOMAIN. That "no" lives for the negative TTL in the zone's SOA record (RFC 2308).

Can someone fake the answer?

Classic DNS is plain, unsigned UDP, so a forged reply can slip in. DNSSEC signs records so resolvers can check them, and DNS over HTTPS or TLS encrypts the hop from your laptop.

Simplified on purpose. Each server drawn is really a set (13 root letters on 2,049 instances, 13 .com servers, 8 for GitHub), and CNAME chains, IPv6 and DNSSEC checks are left out.
