Google hands the site a signed note that says who you are.

You open example.com while signed in to Google, and a card offers Continue as Alex. One tap later the site knows who you are, and you never typed a password.

  2. The cardprompt()

Marked: your server's check, because the note means nothing until the server tests Google's seal. The drawings below zoom into each part.

In plain words. Think of a signed note of introduction. The site asks, the browser shows you a card, and you agree with one tap. Google writes a short note about you, addressed to this site, and seals it. Your server checks the seal and the address, then signs you in.

  1. The page only asks; the browser draws the card.

    In plain words. Your page loads Google's script and calls prompt(). That is a request, not a drawing. The browser shows the card itself, with the Google account it already knows.

    Under the hood. In Chrome the card is browser UI drawn through FedCM, so the page cannot move, style or cover it; the old opt-in flag use_fedcm_for_prompt is now ignored. The card shows only on HTTPS, and only when this browser has an active Google session.

    <script src="https://accounts.google.com/gsi/client" async></script>
<script>
  window.onload = () => {
    google.accounts.id.initialize({
      client_id: "YOUR_CLIENT_ID",
      callback: (r) => sendToServer(r.credential),
    });
    google.accounts.id.prompt();
  };
</script>
    card = One Tap promptscript = gsi/client

  2. One tap, and Google writes a signed note for this site.

    In plain words. You tap Continue. Google writes a short note: who wrote it, who it is for, and who you are. Then it seals the note, so nobody can change a word.

    Under the hood. Your callback gets a CredentialResponse: credential is the ID token, a JWT in three dot-separated parts, and select_by says how you chose (user, auto, fedcm…). With login_uri instead of a callback, Google posts credential to your endpoint with a g_csrf_token that must match the cookie of the same name.

    signed note = ID token (JWT)seal = JWT signatureaddressee = aud (your client ID)writer = iss

  3. Your server trusts the note only after it checks Google's seal.

    In plain words. Anyone can write a note that says "I am Google". Your server tests the seal against Google's public key. Then it reads the addressee, the writer and the date.

    Under the hood. Fetch the keys from https://www.googleapis.com/oauth2/v3/certs and refetch when Cache-Control says, because they rotate. Then check that aud is your client ID, iss is accounts.google.com or https://accounts.google.com, and exp has not passed.

    from google.oauth2 import id_token
from google.auth.transport import requests

info = id_token.verify_oauth2_token(
    credential, requests.Request(), CLIENT_ID)  # seal, aud, exp
if info["iss"] not in ("accounts.google.com",
                       "https://accounts.google.com"):
    raise ValueError("not from Google")
user_id = info["sub"]
    Google's key = public keys (oauth2/v3/certs)seal check = verify_oauth2_token

    Reading the note is not checking it.

  4. File the person under sub, never under the email.

    In plain words. Every note carries a member number (sub). People change emails. The member number stays with the Google Account.

    Under the hood. Google says sub is unique among all Google Accounts and never reused, while one account can have several emails over time. Use email only to find an existing account, and treat it as proven only for @gmail.com addresses, or when email_verified is true and hd is set.

    member number = subdrawer = your user record

    The email is a label. The sub is the person.

Close the card a few times, and it stops showing for weeks.

Without FedCM, each close in a row pauses it longer: 2 hours, 1 day, 1 week, then 4 weeks, until a sign-in succeeds. In Chrome the browser sets the pause, and you reset it from the lock icon in the address bar with Reset Permission.

Push further

What do Safari and Firefox users see?

Google calls them ITP browsers, with Chrome on iOS, and the standard card does not work there. With itp_support: true they get a welcome page, then a pop-up that works much like the card.

Can it sign people in with no tap at all?

Yes: auto_select: true returns a token without a tap when only one Google session has approved your site before. Call google.accounts.id.disableAutoSelect() on sign-out, or the user lands straight back in.

Can I call Google APIs with this token?

No. This sign-in API returns only ID tokens. Reading a user's Drive or Calendar needs an access token from Google's separate authorization API.

Simplified on purpose. One browser and one Google account; the account chooser, the first-time consent page and the pop-up fallbacks are left out.
